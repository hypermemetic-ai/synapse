The raw summary, verbatim off the wire:

  {"description": "Project management subsystem.", "hash": "", "namespace": "pm"}

So: 22 of 23 edges agree exactly, and one disagrees — by advertising no hash at
all. This is not corruption and not a client bug. It is the macro synthesis path:
plexus-macros/src/codegen/activation.rs:594-620 emits `hash: String::new()` for
`#[child]` methods when an activation does not hand-write `plugin_children`, and
says so in its own comment ("the macro has no compile-time hash source for the
child plugin's schema"). `solar` hand-writes `plugin_children` precisely to avoid
this (plexus-substrate/src/activations/solar/activation.rs:145-149); `orcha` does
not, so `orcha.pm` ships an empty hash. Rust serializes it (no
skip_serializing_if), and Haskell decodes it strictly (`o .: "hash"`, no
defaulting) — so the empty string arrives intact as a *value*, not as a decode
failure.

Consequence under the OLD code: navigating to `orcha pm` looked the cache up
under "" (always a miss, nothing is ever stored there) and inserted under
"50bfa7415dec30dd" (which nobody ever looks up). `orcha.pm` was permanently
uncacheable, silently, with no error — exactly the failure mode the ticket
predicted, present on the real wire today.

Two further notes, reported rather than fixed here:

  * `Synapse.Algebra.Navigate` calls `checkCycle (csHash child)` on the same
    advertised hash. With one empty-hash edge on this substrate there is no live
    false positive, but two identity-less children on a single descent path would
    be reported as a Cycle. That is a wire-shaped hazard, not a cache one.
  * A hub's own composite hash folds its children's summary hashes in
    `HashMap` iteration order (plexus-core/src/plexus/plexus.rs:927,
    schema.rs:771-805), so it can vary between boots of byte-identical code.
    Both sides of the comparison above come from ONE substrate process, so this
    does not affect the result — but it means a hash captured from one process
    must not be compared against another's.

All hashes above are 16-hex legacy digests (DefaultHasher, `{:016x}`), not
CONNECTOME-HASH/1. Never compare these against Connectome node hashes.
